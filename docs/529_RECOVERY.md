# 529 服务过载的延后补跑与断点续跑

九组三条件购物评估及旧乙图三组入口，对 HTTP(超文本传输协议) 529 服务过载使用专门的同需求恢复机制。它保留原来的二十条正式需求，不用备用需求替换收到 529 的需求，也不删除已经正常完成的条件结果。普通购物失败、购买了其他商品、达到步数上限，都属于有效观察，不会因为结果不好而重新采样。

## 首次遍历与补跑

1. 某条需求的一个条件在模型请求重试后仍收到 529，先保存该次错误及已有动作轨迹，将这条原需求记入延期队列，跳过它尚未执行的条件，继续其余正式需求。
2. 按不同需求统计连续过载。第一次过载之后，紧接着两条需求也收到 529，即三个连续需求过载，立即保存并退出本次评估。一个需求内的多次请求失败只算一条需求；正常完成一条需求会打断连续计数。
3. 正式需求首次遍历结束后，按延期队列补跑原需求，最多两轮。每轮每个未完成条件最多执行一次，因此三个条件的上限为两轮乘三条件，即六次回合执行。
4. 已提交的有效条件不重跑；第一轮补齐时也不再进行第二轮。这可以少于六次实际执行，而且不会依据购买是否成功挑选结果。
5. 曾收到 529 的需求始终保留原题。如果补跑时又遇到超时或其他可恢复服务错误，仍在这两轮额度内补跑原题，不能转去备用需求；错误记录保留实际错误类型。
6. 第二轮后仍有未完成条件，保存结果与失败记录后退出，终端打印故障需求、条件、轮次、停机原因及账本位置。

上述轮次是完整购物回合的执行次数，不是网络请求次数。一个回合包含多次策略模型调用，每次调用仍有原来的请求级重试。没有遇到过 529 的需求，其其他技术错误继续沿用已有分类与备用处理规则。身份校验失败等不可恢复错误仍立即停止，不能通过补跑掩盖。

## 断点恢复与记录

每组评估目录内的 `deferred_529_state.json(延后补跑账本)`记录固定需求、条件、模型与图片绑定、当前阶段、首次遍历位置、延期队列、已经消耗的补跑轮次、已提交报告和原始失败尝试。账本先写临时文件并同步，再原子替换，降低中断时损坏记录的风险。

恢复粒度为需求与条件。已经提交的有效条件直接复用；中断时未提交的条件从重置后的商城回合重新执行。中断不会把已经消耗的补跑轮次自动清零。阈值停机后，再次手动运行命令代表新的恢复批次，可解除停机并获得新的有限补跑额度，旧批次和旧错误全部保留；同一运行批次不能靠重复调用无限刷新额度。

失败轨迹保存在 `shopping_attempts(各次回合轨迹目录)`；当前条件轨迹继续保存在 `shopping(当前回合轨迹目录)`。累计过载事件与最终有效样本错误分开统计：后来补跑正常的条件会进入正式结果，而此前发生的 529 不会消失。只要仍有缺失条件，就不能把整轮状态或正式目标购买率标成完整结果。

断点恢复依赖相同需求、条件、图片、编码器、模板及评估实现版本。校验发现身份改变时会拒绝混用。评估代码升级后复用以前冻结的历史与图片，使用新的评估变体目录，保留原评估结果。

## 旧乙图三组入口

`-Stage(执行阶段参数)`支持 `Run(完整流程阶段)`、`Evaluate(仅购物评估阶段)`及其别名 `Resume(断点续跑阶段)`。`-Method(优化方法参数)`采用 `ssa(频谱模拟攻击方法)`；`-Root(实验输出目录参数)`指定独立目录。

新实验示例：

```powershell
.\run_old_b_frequency_126.ps1 -Stage Run -Method ssa `
  -Root '.\src\output\old_b_ssa_529_trial01'
```

中断或因 529 阈值停机后，保持同一代码版本与方法参数，执行：

```powershell
.\run_old_b_frequency_126.ps1 -Stage Resume -Method ssa `
  -Root '.\src\output\old_b_ssa_529_trial01'
```

仅评估入口核验已保存的图片与记忆，不重新采集历史或执行图片优化。在冻结运行设置与当前设置相同时，它保持原评估目录，继续其中未完成的条件；如果是允许的评估代码升级，则进入新的评估变体，不覆写旧完整实验结果。最终状态另存于 `evaluation_resume_result.json(评估续跑结果文件)`。

此次代码修改本身不启动真实购物请求，也不补跑或改写已经完成的两轮实验。验证采用模拟过载、模拟中断与本地冻结产物检查。
